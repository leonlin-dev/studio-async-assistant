# 01 · 原理性方案推敲稿

状态：草稿（v0）。本文档是设计阶段的主战场：每个原理以「主张 → 论据 → 反方 → 裁决」的格式推进，裁决结果移入 `docs/decisions/`。

## P1 · 任务是唯一的一等公民

**主张**：系统中一切工作（用户请求、助手自查发现的问题、定时事务）都统一表示为"任务"，拥有同一套生命周期：`draft → active → blocked → delivered → accepted/closed`。

**论据**：用户"只关心一部分内容"的前提，是系统能对全部内容进行统一的优先级排序；只有统一表示才可统一排序、统一升级、统一交付。

**反方**：把临时性、探索性工作强行任务化，会产生大量管理开销，反而违背"让用户少操心"。

**裁决**：待定。

## P2 · 关注模型 = 显式订阅 + 推断过滤 + 免打扰预算

**主张**：用户视野由三层构成：(a) 显式关注列表（用户声明"我要关心这个"）；(b) 助手推断的值得关注项（带置信度，用户可纠正，纠正进入记忆）；(c) 免打扰预算——每单位时间打扰用户的次数上限，超出即降级为静默记录或合并摘要。

**论据**：纯订阅会漏掉重要事件，纯推断会让用户失去控制感；预算把"打扰"变成稀缺资源，逼助手学会合并与摘要。

**反方**：预算是硬编码的产品策略而非原理；也许应该由用户对助手的信任度动态决定。

**裁决**：待定。

## P3 · 异步控制流的三个出口：问、赌、搁

**主张**：任务在任何决策点，助手只有三种合法动作：
- **问（ask）**：升级为用户关注项（消耗免打扰预算）；
- **赌（commit）**：依据已声明的原则/默认值自行决定，决策与理由全程留痕、可回滚；
- **搁（park）**：任务转为 blocked，等待外部事件（用户回复、依赖完成、时间到达）。

不允许的只有一种：无限期地"继续干"而不产生上述三种状态之一。

**论据**：异步系统死法只有两种——要么无限打扰用户，要么静默跑偏。三出口模型保证每个任务始终处于可审计的确定状态。

**裁决**：待定。

## P4 · 交付物先于执行：验收契约前置

**主张**：任务进入 active 之前必须先有交付物契约：形式（文件/消息/PR/数据）、验收标准（可检验的条件）、送达方式。无契约不允许开工；契约可以由助手起草、用户一句话确认。

**论据**："完成用户期待的交付物"中，"期待"必须被外化为机器可判定的契约，否则异步执行无法自检，只能最后靠用户验收，回到同步模式。

**反方**：探索性任务（"调研一下 X"）在开工前无法写出验收标准；需要允许"探索型契约"（产出为发现报告，验收标准是"回答了问题"）。

**裁决**：待定。

## P5 · 记忆按"用户视角"组织，不按任务组织

**主张**：助手记忆的主索引是"每个用户关心什么"，而非历史任务列表。任务结束即归档；只有进入关注模型的事实（偏好、纠正、领域知识、在跟踪的事）被提升为长期记忆。

**论据**：用户回来时的第一个问题永远是"和我关心的事现在怎么样了"，回答它靠的是关注模型索引，不是任务日志。

**裁决**：待定。

## P6 · 信任与权限渐进放大

**主张**：异步代理的权限随"被验证的成功记录"逐步放大：初期多问多搁，交付物连续被验收通过后，同类型决策从"问"降级为"赌"。任何一次被用户否决的"赌"，回滚权限一档。

**论据**：这是唯一能让"少打扰"与"不跑偏"同时成立的机制——两者由同一个变量（信任度）驱动，动态平衡。

**裁决**：待定。

## P7 · 一切后台工作可中断、可观察、可接管

**主张**：任何异步执行中的任务，用户随时可以：查看当前状态与理由、中断、接管为同步会话、改方向后继续。接管后异步上下文不丢失。

**论据**：这是用户信任的技术底座；"只关心想关心的"隐含"想看时随时能看全部"。

**裁决**：待定。
